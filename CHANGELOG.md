# Changelog

## Unreleased

### Storage v2

For people and agents:

- Faster everything: notebooks are answered from memory and the database instead of Git subprocesses. Measured in development: listing a notebook 1.2 ms (was 12.5 ms), the history of a note with 5,000 revisions 1.4 ms.
- Novel-size documents: live editing takes notes up to the ordinary note size limit (32 MiB by default, was 1 MiB). Live snapshots are stored uncompressed, so checkpoints of long notes stay fast: measured in development on a 1.2 MB manuscript with 5,000 revisions, a one-paragraph live checkpoint takes 19 ms and opening the note for live editing 16 ms.
- A new note editor: one CodeMirror 6 editor with three modes. **Visual** is now a live preview instead of Milkdown: formatting shows in place, and Markdown marks appear only on the element the caret or selection touches, as in Obsidian. **Source** shows the complete Markdown, and the new **Side by side** shows Source next to the rendered note (on screens at least 900 px wide). Every mode edits the note's Markdown text itself, so opening a note, switching modes or editing never rewrites, normalizes or renumbers text you did not change; paste inserts plain text exactly as copied, so cells copied from a spreadsheet paste as their text. The editor draws its own caret, a bar in the text colour that holds still while you type and blinks once you pause (it holds still if your system is set to reduce motion), so the caret shows in every mode and theme and in every browser, Safari included (in the dark theme the browser's caret was black on the dark background, so hard to see in Chrome and Brave and invisible in Safari), and a selection shows in the app's selection colour. The browser's autocorrect, auto-capitalization and writing suggestions are off in every mode, so a word is never replaced or capitalized behind your back and the double-space period of phone and Mac keyboards stays the two spaces you typed; spellcheck still underlines words, and one changes only when you choose a suggestion. The same holds wherever else you write text that a note or a comment keeps: comments and replies, quick notes, a note's name and its **Properties**, the terms of a writing glossary, the title of an archived source, the notebook's agent instructions, your assistant's memory files and an employee's responsibilities, and the combined version when you reconcile a draft. In a private draft (a new note before its first save, a version opened in the editor, or a draft kept on this device after a crash or a refused live update), Visual shows each YouTube or Vimeo video as a placeholder naming its host and loads the player only when you choose **Load video**, so opening the draft tells no video host your address or the video; saved notes show their players at once, and Read's preview of such a draft shows the link only. In Visual, a table wider than the screen scrolls sideways in its own box instead of widening the note on a phone, screen readers hear headings with their level, and Tab moves on past task boxes. A line with a very long run of spaces no longer freezes the editor or the rendered preview for seconds. Undo and Redo wait until a phone keyboard or input method has finished composing a word, so they can no longer corrupt a live note mid-word. Any note, a whole novel included, opens whole as one scrolling note, and the editor draws only what is on screen; section mode is gone. Comment highlights and **Comment** work in every mode, and links open with Ctrl/Cmd+click (or **Open** on touch screens). Measured in development on a 1.2 MB manuscript at 4× CPU slowdown, a keystroke paints in about 20 ms in Visual and Source, and opening the manuscript for editing takes about 1 s unthrottled.
- In long notes: Ctrl/Cmd+F searches the whole note, and the browser's recovery draft is written at most every 250 ms instead of on every keystroke.
- Live editing sends only what changed. The browser's live polls, and the answers to its own edits, carry only the change since the version the tab holds instead of the whole note: 340–760 bytes instead of 2.8 MB for a 1.2 MB manuscript. An edit is sent as soon as its keystroke has painted, and another browser's edit now appears in under 70 ms (was about 450 ms). While a note is live, typing no longer copies it into the browser's recovery storage: the draft is stored once and each change is recorded after it, so a crashed or closed tab, or typing offline, still loses nothing. Measured in development on the 1.2 MB manuscript at 4× CPU slowdown, a keystroke paints in 23–29 ms against 55–57 ms before, with no long task while an agent edits the note. Tabs still running the previous version and MCP tools work as before.
- Typing in a long note does less work per key. The editor keeps a note's text in pieces, so a key press in a 1.2 MB manuscript no longer copies the whole note, and the collection badge, Save's label and the live status line update once typing pauses instead of on every key. Measured in development at 4× CPU slowdown, a keystroke in the manuscript paints in 19–20 ms (was 22–28 ms). With the Contents and Comments panel open, a pause in typing no longer uploads the whole note and renders it again (on the manuscript, 1.2 MB and a stall of 100–150 ms at every pause): while you edit, Contents lists the headings of the text you are writing, including one right after a list or a quote, a click puts the caret on that heading, and Show passage selects the passage in the editor. The server keeps a live note loaded between keystrokes and no longer answers a tab's waiting poll with the tab's own edit, so each key one person types is one request, and the gateway's CPU while typing fell to a quarter or less. A Save while live editing answers with only what changed. Edits made while the browser was offline are sent as soon as it is back online, and after a server outage with the server's first answer; a hidden tab sends its last edit at once. A gateway that has not yet heard of another gateway's live edits reads them instead of asking the tab to resend the whole note. During a rolling deploy, tabs on this version keep working against gateways still on the previous release.
- Purge: a notebook Owner or an Admin can remove sensitive content from every version (a whole note, chosen versions, or redacted text). In the browser, **Permanently erase…** is in a note's ⋯ menu, its Version history and the notebook settings. You review a plan, give a reason and get a receipt. Agents can only prepare a purge (`prepare_purge`): they get the plan, without counts of records outside the notebook, and a link for the person to confirm it. A purge also redacts the private chats, Knowledge proposals and judgment records that quoted the content, without anyone reading them, and clears search and other derived data on every gateway. Citations and pins to rewritten revisions keep working, and a pin to an erased version answers "purged". The GitHub copy is force-pushed once for that purge. Operators run purges with `forgetmenote admin purge`. An `export_project_backup` transfer in progress is ended before the purge rewrites the history, and one whose bundle was made just before a purge ends too; both ask to be started again instead of serving the erased content. A browser backup download still being prepared when a purge ran is refused and asks to be downloaded again. See [purge](docs/purge.md).
- A purge plan names another notebook that keeps the content being erased only when you can read that notebook (for an agent, only when its credential also reaches it), and only an Admin's receipt counts what storage deleted, so a purge no longer tells whether someone else's notebook, such as a private Inbox, holds the same file. A confirmed purge runs to its end on the server even when the page is closed or the operator command is interrupted. A purge's text or pattern is at most 64 KiB and it names at most 1,000 notes or versions (413 `too_large`). Each notebook keeps at most 64 plans that agents prepared, and an expired plan, with the text it holds, is deleted within a quarter of an hour. An export that waits too long for a purge is 503 `timeout`, retryable in MCP, and MCP's session and subscription limits are 429 `capacity`; a legacy SSE stream that cannot watch its notebook is refused or told so instead of staying silent.
- A purge plan also says how many commits have the text in their author or committer, which a purge keeps, and, for a whole note, the other notes that may still link to it by name. A text purge redacts only what people wrote, never the notebook's own structure (the IDs and fields of its Trash, lock and comment files, a note's `fmn-id`, the commit trailers that record who made each revision): a plan whose text is found there is blocked and names the file. Notes emptied from the Trash stay out of history search after a purge, and a gateway that has seen a purge no longer serves a revision it erased from its cache.
- An Owner who is not an Admin sees, in a purge plan and its receipt, counts only for their own records (their chats, judgment jobs and citation checks, Knowledge proposals and checkpoints), with a line saying other people's records are redacted too; the purge still redacts everyone's, and a guess at what others wrote gets the same plan whether it is right or wrong. When chat transcripts or judgment records could not be redacted, such an Owner's receipt says so without a number, as they may be other people's; an Admin's gives the counts. The browser's purge dialog shows the plan's warnings and lists the notebook's earlier purges, unfinished or interrupted ones included. A purge refuses to rewrite a notebook whose authority changed after its check, and a handoff is aborted when the notebook moved after it was prepared. A commit message line that only looks like a trailer (`Jane: please keep these`) is redacted as text instead of blocking the purge. A backup export a purge ended is 503 `timeout` (retryable) and a later chunk of an expired export 410 `export_expired`. A receipt the database refused is kept on disk and stored once the database takes it, and a damaged Git export is recreated anew for the purge that rewrote it, flagged to replace a GitHub copy at any commit the notebook's purges rewrote, and swapped in only once complete, so a failed rebuild leaves the old export and its flag as they were. Rewritten commits keep their author and committer names and e-mail addresses, as [purge](docs/purge.md) now says.
- Confirming a purge prepared right after writing no longer fails with "the confirmation does not match this purge plan; prepare the purge again" when the notebook's Git export catches up, or someone opens one of its notes, or a note outside the purge that already holds the text, for live editing, before you confirm. The plan now says the GitHub copy may be force-pushed whenever the export may hold a rewritten revision by the time the purge runs, and the receipt says whether it is; a note the purge changes that is only opened for live editing meanwhile is restarted too, and the receipt counts every live note the purge restarted. A plan must still be reviewed again when the notebook changed, when the content turned up in another notebook or in the live edits of a note outside the purge, when someone types into a note whose live edits the purge would discard, or, for a plan that changes no revision, when someone types the content into a note it covers; the plan now says how many of the notes it restarts lose edits not yet saved, counting edits a long session stored in its live document's snapshot, which it missed before.
- Moves, duplicates, Trash, organization, edit groups and imports commit as one revision or not at all.
- Empty Trash keeps working for the life of a notebook. The Trash manifest kept a record of every note ever emptied or restored, and once it held 10,000 records every further move to the Trash was refused, even right after emptying it. Those records now move to numbered archive files (`.gitnotes-trash-1.json`, …) that still keep emptied notes out of history search, so only notes still in the Trash count against the limit. Moving or renaming a note or folder also rewrites the links of notes in the Trash, so a note restored later still reaches what it linked to; such a move was refused before. It still stops when a note in the Trash came from a location that is now locked. AI organizer moves update the links of notes in the Trash too, on a best-effort basis: a note one may not change (a lock over it or over the location it was trashed from) or whose links cannot be updated safely (wiki or HTML links to the moved note, for example) is left as it is and named in the preview, the activity and the receipt, and the move goes ahead; Undo reverts each such note still unchanged and names, without refusing, one that changed, was emptied or restored, or was locked since. A move made from chat updates the links of notes in the Trash too, where it was refused before: it leaves a note it may not change (a lock over it or over the location it was trashed from) as it is and goes ahead, and tells the chat model only how many notes in the Trash it updated and skipped, never which. The same holds for media that notes in the Trash embed, so a chat can move an `assets/` folder one of them embeds; and a chat move refused because a note outside the chat's notes links into what it moves no longer names that note, nor says whether it is locked. A restore on one gateway no longer drops from the Trash a note another gateway has just moved there, nor lists again one it has just restored. Emptying 2,000 notes from the Trash takes 24 MB of memory instead of about 700 MB. A damaged Trash file is reported as a server error that names the file, to restore from a backup, instead of as a bad request. See [Trash](docs/trash.md).
- Personal Slack collection queues a history page's threads in linear time: with 5,000 pending reads, a page takes about 6 ms instead of about 0.9 s.
- Groundwork for history and blame: a note's history follows renames through its stable ID, and every revision and live update records who made it.
- The browser and MCP now share one definition of each notebook operation they both offer (Trash, comments, live notes, repository sources, retrieval, knowledge review, reading and saving notes), so both answer alike. A caller is authorized before its input is checked, and browser requests are authorized again once their body has arrived. A failed MCP tool call says what kind of error it is in `_meta["forgetmenote/error"]` (`status` and `code`, plus `retryable: true` when the server is busy). A non-Markdown path in `read_note` or `save_note` is now reported as invalid input instead of a permission failure, and `review_inbox` notes that consumer checkpoints are externally reported (`completionMeaning`).
- A chat whose saved sources can no longer be bound to its scope now fails with that scope error instead of "Chat runner stopped unexpectedly".
- Errors are reported by kind on every transport. A catalog, judgments or data connection outage is 503 `unavailable`; it was 500 in the browser and 400 in `/api/v1`. A concurrent change, a changed data operation schema or a chat run that is still active is 409 `conflict`, oversized stored content is 413 `too_large`, text with a NUL character is 400, and a provider that is limiting requests is 429 `capacity` (retryable in MCP). A server failure tells the client only what failed. Its cause, such as a database error, goes to the server log, which now also records the cause of MCP tool calls that fail this way. On an instance without repository sources, `discover_automation_packages` answers 503 `unavailable` instead of invalid input.
- Notebook refusals are typed too: input the caller must correct (an invalid Trash entry, history or revision, an invalid metadata, container, tag or `fmn-id` value, a search or edit group past its bounds, one Trash request too large for even an empty Trash) is 400 `invalid_request`; a notebook limit that frees up again (notes in the Trash, lock rules and the lock policy size, discussions and replies, pending captures, the review inbox, notebook subscriptions, notes open for live editing, live long polls past the notebook's limit) is 429 `capacity`, retryable in MCP; and a limit no retry lifts (a note whose history is too long for the Trash, a change of more than 10,000 paths) is 413 `too_large`, not retryable. They were 500 in the browser and untyped in MCP. Their messages are unchanged, except that a full Trash now says to empty it or restore notes first.
- A save on one gateway can no longer slip past a lock that another gateway set while the save was being checked: it is refused as a conflict. A folder's listing shows items with equal titles in one fixed order (folders first, then by title, then by path).
- Notebooks no longer accept names or commit messages that Git refuses (`git~1` and other spellings Git takes for `.git`, a NUL in an edit group's summary), so every notebook's backups restore; a note an earlier storage v2 build stored under such a name can still be moved, or moved to the Trash alone or by an edit group. A Quicknote filing in progress now blocks an authority handoff after a restart or on another gateway, and a write or filing checked before a handoff on another gateway no longer lands after it. The same holds for live edits: one checked before a handoff on another gateway is refused (the browser keeps it and makes the note read-only), and live edits not yet saved as a version, on any gateway, refuse a handoff until the note is saved. One busy notebook no longer delays other notebooks' notices of new revisions.
- In the browser, moving on from a note or folder before it loads cancels its request, Back from search, Inbox or a settings page returns to where you had scrolled, and a panel that is running an action is marked busy for screen readers while its controls are disabled.
- MCP tools (apart from the new `prepare_purge`, and `move_notes` answers, which also count the notes in the Trash a move updated, `trashLinksUpdated`), `/api/v1` (apart from the error kinds above) and revision IDs are unchanged. Revisions are still Git commit SHAs, and imported history keeps them, so citations and pins stay valid. A contract audit found three intended differences in tool answers: an unknown revision is reported as "not in this notebook's history" instead of a Git failure (same error class); a note's history follows it through Trash and a restore to a new path; and changes since a cursor report a heavily edited rename as renamed rather than deleted and added.

For operators:

- New storage: notebook revisions are exact Git commits in Postgres (migrations `0017` and `0018`), file contents of 8 KiB or more are content blocks in the blob store, and live documents are database rows, their snapshots stored uncompressed (migration `0019`). Git working trees, the write journal, workspace locks and collaboration files are no longer used.
- A bare Git export per notebook, `data/exports/NOTEBOOK.git`, reproduces its history byte for byte. Backup watchers and managed backups push it, and existing remotes continue by fast-forward. A purge's rebuild of the export, and a first export of 100 revisions or more, write one delta-compressed pack instead of many individually synced files: on a slow disk, the rebuild of a 20,000-revision notebook took 69–74 s, against 187–192 s with individual files.
- Importing a notebook bundle gives the import 90 s plus one second per MiB of the bundle (about 17 minutes for a 950 MB bundle), and Git's check of it 90 s plus one second per 2 MiB (about 9 minutes), both counted once the upload has arrived. A browser upload is no longer cut off by the server's 60 s read timeout, nor a long import's answer by its 120 s write timeout. An import that runs out of time is reported as a timeout (503 `timeout`, retryable in MCP), to retry when the server is less busy, instead of as damaged history or a server error.
- Temporary bundles no longer outlive what they were made for. Browser backups are prepared under `cache/backups` instead of the data directory itself. A gateway that starts removes the export and backup bundles and the notebook import uploads that a stopped process left, and a purge removes every temporary bundle on its gateway's disk, since they hold the notebook as it was. Startup leaves every other file in the data directory itself alone, so an operator's bundle kept there, such as `backup-20261123.bundle`, is never deleted (earlier releases' browser backups named `backup-<digits>.bundle` stay there too). A gateway that starts, and every purge, also remove the temporary files a crash left beside content blocks and exports (`.blob-*`) and in the knowledge caches (`.knowledge-*`, `.vectors-*`), which could hold purged content. Maintenance of a notebook's Git export removes the staged pack and temporary files that an interrupted export or rebuild left behind (about 0.9 GB for a 20,000-revision notebook).
- Content blocks nothing uses any more are removed by a scheduled sweep, which every gateway tries about five minutes after it starts and then daily, one gateway per instance at a time: those of a deleted notebook or a failed import, those a refused write stored, and those a purge's own removal could not delete. A purge removes the blocks only it used right after it commits, even when its request has ended, and writes to the notebook go on meanwhile. On a 2,000-note, 20,000-revision notebook a sweep that finds every block in use takes 16 ms. Creating or importing a notebook reserves its ID on every gateway, so a failed import on one gateway no longer deletes a notebook another gateway created meanwhile, nor does a creation take over a notebook an import is still storing. See [Postgres](docs/postgres.md).
- A purge whose gateway stopped after it rewrote the history is listed as `unfinished` by `GET /p/NOTEBOOK/api/purge` and `forgetmenote admin purge list`, with what it did not do. A gateway that starts finishes what needs none of the erased content (search and Knowledge indexes, prepared plans, bundle exports) and keeps an `interrupted` receipt, and the notebook's next Git export rebuilds the export for that purge and flags it. While a notebook's files from the previous release (its old working tree and `.git`, `collaboration/`, `captures/`, `write-journal.json`) are still in the data directory, a purge's plan and receipt say that no purge reaches them. See [purge](docs/purge.md).
- One stopped cutover per instance: `forgetmenote admin storage import`, `verify`, `export` and `check`. The release refuses to start until every notebook in the catalog is imported, while a notebook's import did not finish, and while a notebook's old Git repository has commits its stored history lacks (the previous release committed after the import). An import that was killed, ran out of memory or lost the database part way resumes when it runs again (`resumed`) instead of being refused for good. Once the new release serves the notebooks, `forgetmenote migrate -finish-rollout` raises the database's reader version to 2, so a container left on the previous image refuses the instance instead of serving the notebooks from their old repositories; restoring the freeze dump for a rollback undoes it. Right after the new release starts, `forgetmenote admin storage check` proves beside it, reading only, that every notebook is served as its repository holds it: the same history with every object proven, an export at the repository's `HEAD` that passes `git fsck --strict`, every file at `HEAD` read through the server's read path byte for byte, and each note's whole history as the server lists it. A notebook someone wrote to after the start is proved the same way at the repository's `HEAD` (`passed at Git HEAD`), but only when `HEAD` is the commit the import recorded, so an older copy of the data directory fails. It prints one JSON line per notebook and a summary that counts each status and the notebooks compared, passed, failed and skipped, and exits non-zero on any difference, when it compared no notebook at all (a wrong `-data`, or a run after `retire`), and for a `-notebook` that nothing holds. No purge reaches the previous release's working trees and `.git`: as soon as `check` passes, stop the instance and run `forgetmenote admin storage retire`, which checks again that the store holds each notebook's repository history and, with `-yes`, records and removes them (`check` then reports the notebook `skipped: retired`, and fails for a repository that went missing without retire), keeping every file of a notebook it cannot verify or whose files hold work the history lacks. `check` proves the cutover only before `retire`. A rollback still works after that, from the freeze's data archive and bundles. Before pointing a backup watcher at a bare export, install this release's `deploy/git-backup/watcher.py`: an older watcher fails there with `fatal: this operation must be run in a work tree`. The import ends by gathering the notes store's statistics, so the first history reads after the cutover are not planned as scans (about 130× slower before, measured in development). Notes keep their `fmn-id` identities, and other files and notes without one keep theirs through every rename Git detects, edits included, so their history reads as before. The cutover was rehearsed on copies of a production instance's five notebooks: the import took 1.6 s, and every note and history entry read back as before. See the [storage v2 cutover](docs/storage-cutover.md).
- A full backup is now the database dump, the blob store and the data directory, taken together ([backups](docs/backups.md#complete-instance-backup)).
- A stopping server ends at once the requests that wait for changes (open pages' live polls and chat event streams, MCP subscription streams), which reconnect to the next process, so they no longer hold the shutdown for its whole 15 s; every other request in progress, such as a save, an upload, an import or an MCP tool call, still has the whole 15 s to finish.
- Notebook owner processes, `forgetmenote owner`, `OWNER_MAP_FILE` and `notebooks.owners`, `admin move-notebook` and `admin rollback-live-storage` are removed. Every change is one database transaction, so several gateways of one binary serve an instance without them.
- The Git notebook backend is removed from the release. Notebooks are read and written only through the database, and the server runs `git` only for the Git export and bundles, repository sources, and the cutover's import and checks.

### Other changes

- Recoverable content durability, explicit application startup and complete cleanup.
- Bounded live-edit notifications and append/replay/compaction; batched Git reads.
- Isolated catalog clones, separate activity/logo storage and tested storage rollback.
- Concrete shared request, source, Inbox, backup and data-operation owners.
- One local/remote notebook contract, separate chat wire formats and bounded index retention.
- Sectioned instance configuration, accurate runtime summaries and configurable admission.
- Fingerprinted browser assets, full-glyph WOFF2 fonts and shared UI ownership primitives.
- Routable settings, people and timestamps, note context, clearer navigation and accessible themes.
- Evidence-preserving search previews with bounded presentation and explicit ambiguous-context fallbacks.
- Notebook API/MCP aliases using the same authorization and revision checks.
- Fast PR verification, manual full and release checks, advisory scans on pushes to main and next and weekly, pinned actions and reproducible Debian snapshots.
- Current documentation index, archived implementation records and truthful runtime/security claims.
- Python automation packages sandboxed by default (Linux Landlock, no instance files or sockets), with an explicit `"sandbox": false` opt-out per installation.
- Automatic notebook search ranks independent keywords with the chat BM25 index, then partial-word matches; Text stays a literal phrase match. Pressing Enter can ask for a judgment ranking of the leading results once.
- The Jev feature is now called judgments: it is provider-neutral, and TypeSafe's Jev is one decision model it can use. Its routes move from `/api/jev/*` to `/api/judgments/*`; each former path serves the same route with the same checks for one more release. The `jev_*` tables, the `jev` configuration keys and the `jev` smoke scenario keep their names.
- An instance can turn off judgments, data connections and archived sources with `modules.off` in `instance.json`. An off module offers no tools, its routes answer 404, it runs no workers, reads none of its settings and keeps its data, which account deletion and purge still reach; the browser leaves out its controls and Administration says it is off. With archived sources off, startup retires leftover source jobs and their uploads at once, since nothing could resume them. The other modules cannot be turned off yet. See [instance configuration](docs/instance-configuration.md).
- An instance can also turn off repository notebooks (`repositories`) and managed backups (`managed-backups`). With either off, its GitHub App settings stay unread and its webhook or backup worker endpoints answer 404; the GitHub connection flow runs while one of them is on. Disabling a person still pauses the repository sources they connected, and offboarding still lists their repository and backup connections. Document reading and notebook link tools no longer belong to repository sources: they stay with every module set.
- Every module can now be turned off: notebook chat (`chat`), automations, task queues (`tasks`), Slack messaging (`messaging`), personal assistants (`personal`) and agent memory (`memory`), and with every module off an instance runs its notebooks alone. A run that needs an off module is neither scheduled nor claimed and stays queued; a person can still pause their assistant, withdraw its AI processing consent, turn off memory or reply reminders and remove a Slack link, and a purge still redacts chat transcripts. Each gateway records the modules it turns off, and while live gateways disagree each logs a warning and Administration lists every gateway with its set.
- What tells an agent which tools to use now follows the modules too: the MCP instructions, the descriptions of the remaining tools and the Claude Code and Codex packages an instance offers for download name no tool of an off module, and the Claude Code package's memory hook comes only with memory. `find_recipes` is a notebook read and stays with automations off, without the health of the checks that verify recipes. [Feature modules](docs/modules.md) describes each module, what it requires, what turning it off removes and what it keeps, and the [deployment guide](docs/deployment.md#instance-configuration-and-modules) shows an `instance.json` with modules off.
- Folders can move to Archives or Drafts and back. Search leaves Archives out by default, as it does Trash; cancelled requests log as 499 instead of 500.
- Connected agents can extract archived sources themselves. `archive_source` and the source preview take an agent's own extraction of the original it uploads: `text` with a `unit` and numbered `sections`, and an `extractor` naming the agent and model. The original is still required and stored; the text replaces the server's extraction and is recorded as `client-supplied` and unverified, with its checksum. `source_formats` says per format whether the server extracts it or the agent should (`extractedBy`), the MCP instructions and the source tools say when and how to upload an extraction, and `list_sources_awaiting_text` (also `GET /p/NOTEBOOK/api/sources/awaiting-text`, Read) lists sources whose extraction failed or found no text, for an agent to refresh with its text. A refresh that gives no title now keeps the source note's title, as the browser already did. Source jobs (`prepare_source`) run server extraction only and refuse text. The companion is 0.3.5. See [archived sources](docs/sources.md#agent-extraction).
- The server no longer OCRs, transcribes, describes images or converts Apple documents; connected agents do. Images, audio, video, Pages and Keynote files are archived as their originals (`original-only`), and PDFs read only their text layer: a PDF with no text layer is `no-text`, and one with scanned pages is `partial`, naming the pages. `list_sources_awaiting_text` lists all of them. Removed: local Tesseract OCR and hosted OCR, hosted figure and image descriptions, hosted transcription with FFmpeg, PDF page rendering, and the libetonyek Pages/Keynote converter, with the `iwork` and `ocr` build integrations, the archive dialog's hosted options and the three source switches in Administration → AI features. The release image is less than half its former size (1.02 GB to 437 MB unpacked, measured on arm64). Existing source notes keep their text; refreshing one without `text` stores the original, which then waits for an agent. A source job left asking for hosted processing opens as interrupted and cannot be resumed. `describeImages`, `externalOCR`, `transcribe`, `firstPage` and `lastPage` are refused as unknown fields; a chat configuration's `sources` block is ignored with a warning, and `FMN_OMIT=iwork`/`ocr` leaves nothing out.
- In the browser, the instance's chat can read an image you archive. After a PNG or JPEG upload is stored, the server has the chat model transcribe its text and describe it, and stores that as the source's text, labelled with the model and as unverified. It is off until an admin turns on **The chat reads images uploaded as sources** (`uploadReading`) in Administration → AI features, a new switch of its own: AI writing does not imply it, and the removed hosted OCR and description switches do not carry over. It needs a chat connection that reads images, runs under the checks of any hosted AI call, and costs one paid step per upload. Audio, video, Pages, Keynote, PDFs and other image formats are not sent to the chat; for them, and whenever a check refuses, the archive dialog says why and the source waits for a connected agent. See [the in-app chat reads uploaded images](docs/sources.md#the-in-app-chat-reads-uploaded-images).

Storage updates require a completed stopped-instance backup and the recovery
procedures in [storage migrations](docs/storage-migrations.md). A changelog entry
